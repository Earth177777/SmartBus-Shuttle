## Required starting point

**Every developer and assistant MUST read `webtinousQA/webtinousstandard.md` before starting project work.** It is the navigation and working-record guide for this collection. Then read SOFTWARE.MD and the modules relevant to the task; a standalone BUILD.MD invocation retains its essential release checks. Reuse current accepted decisions and read the project's actual instructions. If a required guide is missing, identify it and obtain the needed file before dependent work; do not claim to have read unavailable instructions. Continue useful independent inspection while waiting.

## Professional commercial acceptance

**Commercial delivery requires demonstrated readiness.** Use the core release gate in SOFTWARE.MD and this module's acceptance checks. Define the actual audience, supported environment, acceptance criteria, responsible reviewer, and material risks. Verify critical success, failure, recovery, and permission boundaries that apply. A build, attractive presentation, generated checklist, or installed technology alone does not establish readiness.

Required checks must have actual results and traceable evidence under `webtinousQA/`. Release-blocking failures remain blocked. Label prototypes, drafts, simulations, partial results, and unverified claims accurately; do not present them as production deliverables. Follow the accepted project architecture and choose new major technologies only through the core decision policy.

## Commercial release gate

For a commercial or production release, establish the applicable requirements before implementation and retain the final disposition in `webtinousQA/reports/`. Record the artifact/version, source identity, environment, owner/reviewer, actual checks, evidence links, unresolved issues, and release decision. Small products can use a concise record; their required behavior and protection still need evidence.

| Area | Required evidence where applicable |
| --- | --- |
| Functional correctness | Critical workflows and business rules pass representative end-to-end and negative checks. |
| Security and privacy | Trust boundaries, permissions, secrets, dependencies, sensitive data, and relevant network/certificate controls pass review and checks. |
| Reliability and recovery | Failure, restart, retry, partial outcomes, important data restore, and rollback/forward recovery are verified to the agreed scope. |
| Usability and accessibility | Actual content, errors, supported devices, input methods, and relevant assistive technology are reviewed. |
| Delivery and operation | Supported install/build/distribution path, safe configuration, artifact identity, operational ownership, diagnostics, and support instructions are established. |
| Commercial integrity | Product claims, third-party asset/dependency rights, attribution, supported platforms, and any required assurance statements are accurate. |

A known critical or high-severity security defect affecting the release, material data-loss risk, broken critical workflow, unmet safety requirement, exposed secret, or failed mandatory release control blocks release until resolved or shown with evidence not to apply. Do not self-waive mandatory safety, legal, contractual, or project controls. Eligible lesser deviations require a named accountable owner, explicit scope/risk, compensating controls, and a review/remediation trigger; they are not passing test results.

Production readiness is an evidence-backed decision for a particular release and environment. It is not a universal certification conferred by these documents. A code or documentation change does not authorize deployment, publishing, spending, or production data mutation beyond the user's existing authorization.

## Documentation workspace

**Use `webtinousQA/` at the codebase root** for Markdown documents, decisions, mind maps, diagram sources/renders, reports, and QA evidence generated by these standards. Create only the subfolders needed. Keep an index at `webtinousQA/README.md`. Tool-required files retain their required locations and are linked from that index. Existing canonical documentation can be linked rather than duplicated or moved automatically. Never place real secrets or unnecessary private data in the workspace.

### Workspace layout and ownership

The folder name is exactly **`webtinousQA`**, including capitalization. This directory convention is selected by these standards; routine creation does not require repeating a technology-choice question. Use paths relative to the codebase root.

```text
webtinousQA/
  README.md          # index, scope, ownership, current findings
  standards/         # the adopted Webtinous standard files
  documentation/     # generated project guides and specifications
  decisions/         # accepted choices, assumptions, and exceptions
  maps/              # mind maps, architecture maps, editable sources and renders
  reports/           # QA reviews, benchmarks, release and investigation reports
  evidence/          # sanitized check records, screenshots, and supporting artifacts
  assets/            # documentation images, banners, and shared visual assets
```

This is a responsibility map, not a demand for empty folders. Preserve the editable source of a diagram or mind map beside, or clearly linked to, its rendered image. Use formats supported by the accepted tools; a particular mapping application is not required.

Every generated item should be findable from the index or a linked collection index. Record what it covers, the relevant source/version, and material verification limits. Keep generated and hand-maintained material distinguishable. Update affected links when paths change.

For a file that a tool requires at another location, keep its canonical file there and link it from the workspace index with a short explanation. Avoid maintaining two competing copies. Source code, production data, credentials, dependency folders, and runtime caches are not QA documentation and do not belong here merely because these standards were used.

## Start here

**Use the existing project first.** Inspect its active implementation, setup, configuration, and accepted decisions. This standard does not select a stack, add a feature, or authorize a rewrite by itself.

- **Existing choice:** continue it within its accepted scope without asking again. Distinguish active decisions from abandoned experiments or unused packages.
- **Unresolved major choice:** ask before adopting a language/runtime, framework, database, Docker or another packaging approach, hosting, authentication architecture, external/paid service, or substantial dependency.
- **Already explicit:** a choice in the user's request is accepted for its stated scope. Routine implementation details within that approach do not require repeated questions.
- **Record and reuse:** preserve the accepted option, scope, rationale, limits, and status in the project's decision record. Project A's choices do not automatically apply to Project B.
- **Revisit only for a material change:** ask when requirements, conflicting evidence, or the proposed scope invalidate the earlier decision. A proposal or silence does not resolve a pending choice. Continue useful independent work while waiting.

**Requirement language:** MUST is required within the applicable scope; SHOULD permits a justified exception; MAY is optional. Mark irrelevant modules **Not applicable** with a brief reason when material. Scale the process to the task and risk; do not create unused systems or empty documents.

## Workflow gates

**These are evidence checks, not five approval requests.** Apply them to the current task. A small correction may satisfy several gates in a few sentences; a high-risk change needs stronger records. Reuse evidence that remains valid.

| Gate | Ready to proceed when | Ask the user when |
| --- | --- | --- |
| **1 · Understand** | Outcome, current state, scope, constraints, and acceptance criteria are sufficiently clear. | A consequential ambiguity cannot be resolved from the request or project. |
| **2 · Decide** | Applicable major choices are established or explicitly accepted and recorded. | An unresolved major choice or material change needs a decision. |
| **3 · Implement** | Work follows the accepted scope and accounts for relevant compatibility, data, and recovery needs. | The necessary action exceeds existing authorization or changes the agreed outcome. |
| **4 · Verify** | Relevant checks have actual results; defects and limitations are assessed. | A blocker needs a user decision, missing access, or a material change of requirements. |
| **5 · Deliver** | Agreed outputs exist, documentation agrees, and remaining limitations are visible. | Publishing, deployment, or another final action still requires authorization. |

Use **Passed**, **Blocked**, or **Not applicable** with an appropriate reason/evidence. A failed required check leaves its gate Blocked; a risk exception is not a passing test. Do not report a partially completed task as complete. Gates never authorize actions that the user has not authorized.

## Reverse-prompt: confirm the task you are actually solving

Before substantial work, briefly state **the intended outcome**, **what already exists**, **what will change**, **important constraints/non-goals**, and **how completion will be checked**. Base this on the request and project evidence. Label assumptions and unknowns.

For a new or ambiguous project, bundle material unanswered questions and a recommended approach into one short intake. For a routine change in an established project, keep this brief and do not restart discovery unnecessarily. The user does not need to approve every summary; wait only where a real decision or required authorization remains unresolved.

## Module selection

Use REQUIREMENTS.MD to define the product and acceptance criteria, TESTING.MD to plan and record verification, and OPERATIONS.MD for applicable release/operational procedures. **Use BUILD.MD to prepare a production release package.** BUILD.MD includes a standalone intake and version decision so it can be supplied on its own.

Always include this core file. Add DESIGN.MD for interfaces, CIA.MD for security and assurance, MD.MD for documentation, MAINTENANCE.MD for refactoring or performance, and the relevant optional hardware, video, contextual-help, or mapping module.

## 1. Purpose and applicability

**Build the simplest system that safely meets the agreed need.** Quality means correct behavior, understandable code, appropriate security, reliable operation, usable interfaces where present, and evidence that the relevant requirements work.

Before substantial implementation, establish the problem, intended users, required outcome, constraints, supported platforms, scope, and acceptance criteria. A small script may need a short README; a critical service needs deeper design and operational records. Applying this standard to an existing project does not authorize a rewrite, infrastructure migration, or full repository reorganization.

## 2. Architecture and technology selection

**Follow the adoption and project-decision rules above.** No project is required to use Docker, a server, database, cloud, framework, microservices, queues, Redis, or a particular package manager. Reuse established project tools where suitable. If a new project needs a major choice, present a recommendation and obtain the user's decision before adopting it.

Document relevant components, boundaries, interfaces, sources of truth, dependencies, failure modes, and important trade-offs. Use diagrams when they clarify the system. Record significant decisions and supersede earlier decisions rather than silently rewriting their history.

## 3. Code and repository quality

**Use predictable organization, clear names, focused responsibilities, and the conventions of the chosen language and ecosystem.** Keep related behavior together. Avoid hidden side effects, accidental duplication, speculative abstractions, circular dependencies, and unexplained magic values.

Use the project's formatter, static analysis, type checks, and lockfiles where supported. Type checking does not replace validation of external data. Validate input at the boundary that actually controls the operation, whether that is a service, CLI parser, file importer, native process, or device firmware.

Review dependencies for purpose, maintenance, license, security, compatibility, and resource cost. Do not add infrastructure or substantial dependencies merely because this standard names a capability.

## 4. Security and privacy

**Identify trust boundaries, sensitive information, and likely misuse.** Protect secrets outside source, public bundles, logs, screenshots, and deliverables. Use synthetic examples and sanitized configuration templates.

Where identity or restricted actions exist, enforce authentication and authorization at the authoritative boundary. UI visibility is not an access control. Consider resource ownership, tenant scope, revocation, and expired credentials. Do not add accounts to a tool that does not need identity.

Use safe query, command, path, and output handling. Apply encrypted transport, session protection, headers, origin policy, throttling, and upload controls when their corresponding network or browser surface exists. Use established cryptographic and platform facilities. CIA.MD defines the security and verification approach; unrelated controls may be Not applicable.

## 5. Data and interfaces

**Where persistent data exists, define ownership, schema, validation, identifiers, retention, deletion, and recovery.** Use constraints and transactions where appropriate. Treat caches and projections as distinct from authoritative records.

Schema or format changes need a reproducible transition and compatibility plan. For destructive or irreversible changes, identify prerequisites, safeguards, verification, and recovery limits before execution.

For APIs, libraries, file formats, messages, or device protocols, document the actual contract, errors, compatibility expectations, and supported versions. Use bounded pagination or streaming where unbounded output would create a resource problem.

## 6. Reliability and errors

**Handle expected failures intentionally.** Explain what happened and the useful next action in user-facing output; keep sensitive internals out of ordinary responses. Preserve enough sanitized diagnostic information to investigate failures.

Use timeouts for potentially unbounded external work. Retry only when safe, with bounded attempts and appropriate delay. Account for ambiguous outcomes and idempotency. Protect shared state from races using the simplest adequate mechanism. Queues, circuit breakers, distributed locks, and redundant infrastructure are conditional techniques, not default requirements.

## 7. User experience and accessibility

For a GUI, provide clear hierarchy, accessible controls, visible focus, understandable loading/error/empty/success states, and usable behavior on the supported devices. For a CLI, provide clear help, stable exit codes, useful errors, and an appropriate noninteractive mode. For a library, prioritize a clear API and examples. Headless software does not need a visual interface.

Use the project's approved accessibility target and platform guidance. Apply the relevant interface sections of DESIGN.MD. Webtinous branding is required; an icon vendor, multiple themes, a mobile app, or an in-app assistant is included only when part of the project scope.

## 8. Verification and performance

**Verify changed behavior and critical boundaries using meaningful checks.** Select unit, integration, end-to-end, security, performance, hardware, or manual checks according to the actual risk. Do not create tests that merely repeat implementation or chase a universal coverage percentage.

Use isolated data and environments. Record which checks ran, their scope, actual results, and remaining limitations. A build or mock test alone does not prove deployment, integration, or production readiness.

Set performance expectations appropriate to users and target hardware. Measure a representative baseline before substantial optimization. MAINTENANCE.MD covers investigation and evidence.

## 9. Delivery and operation

**Document the supported installation, execution, build, distribution, or deployment path.** A script may be delivered as a file; a library as a package; firmware as a device image; a service as a deployment. Docker is one option only when accepted for this project.

For deployed or important persistent systems, define safe configuration, environment separation, migration, release verification, rollback or forward recovery, monitoring, and ownership. Define backup and restore expectations where data loss matters. Recovery objectives and service levels come from actual requirements, not universal numerical defaults.

Use CI where it supports the project's workflow. For a release requested through BUILD.MD, use its confirmed major/minor/patch version policy and production gates. Routine source or documentation edits alone do not trigger a release. Preserve explicit existing authorization for publishing or deployment; package preparation alone does not authorize those actions.

## 10. Completion and documentation

A change is complete when its agreed behavior works, relevant checks have actual results, affected documentation matches, and material risks or unfinished work are visible. A release additionally needs the applicable delivery and operational checks.

Maintain useful setup, architecture, decisions, known issues, and release history in proportion to the project. MD.MD governs documentation. Preserve unrelated work and truthful historical records. Do not claim a system is secure, compliant, fully supported, or production-ready without evidence for that claim.

## Practical examples and reference

### Worked example: the Docker decision

**Project A already uses Docker:** inspect the active container definitions, setup instructions, and supported workflow. Reuse that approach for routine work. Do not ask the same Docker question again or introduce a competing environment incidentally.

**Project B is new:** first establish whether it is a script, library, app, service, device project, or another deliverable. If packaging is an unresolved major choice, explain whether a native runtime, container, or another approach fits the actual need. Ask the user, record the answer, and proceed. Do not create a Dockerfile while its adoption is still pending.

**Project A needs a material change:** adding an external service, changing the production platform, or substantially redesigning packaging can exceed the earlier decision. Explain the trigger and consequences before changing it.

### Minimum decision record

| Field | Record |
| --- | --- |
| Decision and status | Proposed, accepted, established from active project evidence, or superseded. |
| Scope | This project and the relevant environments/components. |
| Basis | User instruction, accepted record, or active project evidence. |
| Rationale and trade-offs | The need served, alternatives considered, and meaningful costs/limits. |
| Review trigger | What future change would require reconsideration. |

An established decision inferred from active project evidence should be labeled as such. Do not fabricate a historical approval or infer that an unused file expresses the owner's current preference.

### Match the deliverable to the program

A script may need input validation, useful errors, a safe execution path, and a concise README. A library additionally needs a clear consumer contract and compatibility policy. A service may need deployment, monitoring, and data recovery. An embedded device may need firmware recovery and physical validation. Add the relevant modules according to the actual scope.

## Acceptance checklist

- **Scope:** The requested outcome and supported project type are clear.
- **Decisions:** Major choices are established or accepted; pending choices remain explicit.
- **Behavior:** Critical success, failure, and relevant boundary cases are checked.
- **Protection:** Relevant data, permissions, privacy, and recovery needs are addressed.
- **Evidence:** Actual checks and limits are recorded; documentation matches the delivered result.
