## Choose the workflow

**Refactoring** preserves intended behavior unless a change is accepted. **Optimization** requires an evidenced performance problem and a comparable measurement. A task can use both workflows, but their success criteria remain distinct.

## Part A — Refactoring and maintenance

### 1. Purpose and scope

Refactor to address a concrete problem: confusing responsibilities, repeated defects, difficult change, harmful coupling, unsupported dependencies, or another evidenced maintenance need. Do not rewrite working software solely because a different style or framework is preferred.

Define the intended improvement, affected scope, acceptance criteria, compatibility obligations, and exclusions. Inspect the current implementation, relevant documentation, tests, and user changes before editing. Adopting this file does not authorize a rewrite or migration.

### 2. Preserve intended behavior

**A refactor preserves intended externally observable behavior unless a behavior change is approved.** Distinguish restructuring from bug fixes, features, performance changes, data transitions, and breaking changes. Record intentional differences and relevant compatibility effects.

Keep public APIs, file formats, command behavior, configuration, data, permissions, and supported workflows stable within the agreed scope. Do not freeze an accidental bug as policy; record the discrepancy and resolve the intended behavior where it matters.

### 3. Design and code quality

**Prefer clear names, focused responsibilities, explicit dependencies, and cohesive modules.** Reduce harmful duplication and coupling without inventing speculative frameworks. Shared abstractions need a real common responsibility, not superficial similarity.

Avoid universal function-length limits, compulsory class patterns, or arbitrary directory structures. Use the language and project's established conventions. Remove dead code only after checking actual consumers and dynamic use. Update references when moving files or changing exported symbols.

Keep necessary comments focused on reasons, constraints, and non-obvious behavior. Give temporary compatibility code a clear purpose and removal condition.

### 4. Security, state, and concurrency

**Preserve validation, access control, tenant isolation, secret handling, auditability, and operational visibility.** A cleaner call path must not move authority into an untrusted client or omit checks on an alternate path.

Review async ordering, cancellation, retries, idempotency, transaction boundaries, shared state, and external side effects where relevant. Do not turn partial success into a misleading success result or lose recovery information.

### 5. Data, contracts, and migrations

For data or schema changes, assess existing records, compatibility windows, backfill, ordering, verification, and rollback or forward recovery. Document destructive limits. Treat data recovery separately from restoring application code.

For public contracts and shared components, identify consumers and the accepted deprecation/version policy. Incremental migration, compatibility adapters, or feature flags may help a complex change; they are conditional techniques and do not justify new infrastructure by themselves.

### 6. Technology and dependency changes

**Continue accepted project choices.** A routine refactor does not authorize switching language, framework, package manager, datastore, hosting, or packaging. Ask before a material technology migration or substantial dependency adoption unless it is already authorized.

For an accepted upgrade, inspect compatibility, supported APIs, security, lockfiles, and migration notes. Keep the scope coherent and explain any required behavior changes. Do not install Docker, a queue, or a new service as an incidental cleanup step.

### 7. Verification and change management

**Establish a relevant baseline.** Existing tests, representative manual checks, and characterization tests can help when behavior is unclear. Add meaningful coverage for risk; do not create tests that merely mirror the new implementation.

Use focused, reviewable steps. Preserve unrelated changes. Run checks appropriate to the edited boundaries and regression risk, including failure paths where material. Compare relevant performance where the change could affect it; avoid asserting improvement without measurements.

For a broad or critical change, define checkpoints and a recovery plan. Deployment, production mutation, and publishing follow their own accepted workflow; they are not automatic parts of refactoring.

### 8. Documentation and completion

**Update affected architecture, interfaces, setup, decisions, and operational guidance.** Record meaningful user-visible changes according to the project policy. Do not bump a version or create a release merely because code moved.

The refactor is complete when the agreed improvement is evident, intended behavior and security remain intact within the checked scope, relevant checks have actual results, compatibility and data effects are addressed, and limitations are visible. Stop when the stated problem is resolved rather than expanding into unrelated cleanup.

### Practical examples and reference

#### Change classification

| Change | Additional concern |
| --- | --- |
| Internal restructuring | Preserve intended observable behavior. |
| Bug fix | Document the corrected behavior and relevant regression evidence. |
| Public contract change | Identify consumers, compatibility, and release policy. |
| Data transition | Define existing-record treatment, ordering, verification, and recovery. |
| Framework/infrastructure migration | Resolve the major decision and operational consequences first. |

A single task may contain more than one class. Make the differences visible rather than hiding behavior changes under a refactor label.

#### Practical sequence

Inspect the current execution path and relevant consumers. Establish a focused baseline. Change one coherent boundary at a time where possible. Check the behavior that could regress, including material failure paths. Remove temporary adapters only when their consumers and removal conditions have been addressed.

For uncertain legacy behavior, a characterization check can record what currently happens. It does not declare every observed quirk to be correct policy. Distinguish a known defect from the behavior the refactor must preserve.

#### Stop condition

The stated maintenance problem should be resolved with appropriate evidence. Newly discovered unrelated cleanup becomes a separate proposal unless it is necessary to complete the accepted scope. Do not expand a small restructuring into an unrequested rewrite.

### Acceptance checklist

- **Reason:** The maintenance problem and intended improvement are concrete.
- **Behavior:** Intentional changes are separated from preserved behavior.
- **Boundaries:** Contracts, data, authority, concurrency, and recovery receive relevant review.
- **Checks:** Baseline and post-change evidence cover meaningful regression risk.
- **Scope:** Unrelated work is preserved and unnecessary migration is avoided.

## Part B — Performance investigation and optimization

### 1. Goal and baseline

**Optimize an observed problem or agreed performance requirement.** Define the affected workflow, user impact, target environment, representative workload, current measurement, and desired outcome. A new benchmark, coverage percentage, or latency target is not universal policy.

Measure before substantial optimization where measurement is feasible. If direct measurement is unavailable, label the hypothesis and limitation. Do not report a predicted improvement as an observed result.

### 2. Reproducible evidence

Record the source version, relevant configuration, hardware/runtime, dataset shape, load, measurement method, sample count, and result variability. Protect private data. Compare equivalent environments and separate cold start, warm operation, caches, and external-provider effects.

Use metrics relevant to the problem: latency distributions, throughput, startup, memory, CPU, energy, storage I/O, network use, build time, frame responsiveness, or error rates. Average latency alone can hide important slow cases. Benchmark results must state their scope.

### 3. Find the constraint

**Trace the real critical path with appropriate profiling, timings, query plans, logs, or device tools.** Distinguish CPU work, waiting, contention, excessive transfer, repeated work, memory pressure, and slow dependencies. Change the evidenced bottleneck before adding infrastructure.

Use existing tooling and the accepted architecture. A new profiler service, cache, CDN, worker, database, GPU dependency, or hosting tier is a major choice when it materially changes the project; obtain the required project decision before adoption.

### 4. Apply relevant techniques

Only use techniques whose component exists and whose benefit fits the evidence:

- UI: reduce unnecessary rendering, expensive layouts, oversized assets, and avoidable network work. Consider lazy loading or virtualization while preserving accessibility and state.
- Backend and libraries: improve algorithms, bound work, remove duplicated operations, use appropriate batching, and avoid blocking shared execution paths.
- Data: inspect actual queries, N+1 access, projections, indexes, joins, transactions, pagination, and connection behavior. Account for write, memory, and maintenance costs.
- Network and storage: right-size payloads, compress suitable content, stream large transfers when appropriate, avoid redundant requests, and preserve correct partial-failure behavior.
- Native and embedded: assess target CPU, memory, power, thermal limits, startup, communication, scheduling, and device constraints using representative hardware where needed.
- Build and distribution: review dependency size, repeated tasks, generated output, and reproducibility without changing the product's compatibility contract accidentally.

Framework-specific memoization, utility libraries, Redis, horizontal scaling, queues, and concurrency are possible techniques rather than required solutions.

### 5. Caching and concurrency

Every material cache needs a purpose, authoritative source, key/scope, freshness or invalidation rule, capacity, sensitivity policy, and failure behavior. Do not leak one user's or tenant's results to another. Include invalidation and cache misses in verification.

Concurrency needs bounds, cancellation, backpressure where relevant, and protection against races or resource exhaustion. Parallelize independent work only when safe. A faster happy path must not create duplicate external actions or inconsistent data.

### 6. Preserve quality

Do not silently weaken authorization, input validation, data integrity, privacy, accessibility, useful diagnostics, output quality, or recovery for speed. Explain material trade-offs and obtain the applicable decision before changing requirements.

Maintain appropriate error rates and resource headroom. A system that responds quickly by dropping required work has not met its original performance requirement.

### 7. Validate and operate

**Re-run comparable measurements after the change.** Check correctness, failure modes, resource cost, and regression risk. Use load, stress, soak, browser, provider, or physical tests only when justified and permitted for the environment. Do not direct load tests at live users without appropriate authorization.

Introduce performance checks or monitoring where the problem warrants continued protection. Thresholds should tolerate normal variation and reflect user outcomes. Do not build a monitoring platform for a one-off script by default.

### 8. Documentation and stop condition

**Record the original problem, baseline, hypothesis, change, measured result, trade-offs, verification, and remaining uncertainty.** Update affected configuration and operating guidance. Preserve relevant benchmark history.

Stop when the agreed outcome is met or further work no longer justifies its complexity and cost. If the hypothesis fails, report the result honestly and avoid keeping an unnecessary mechanism merely because it was implemented.

### Practical examples and reference

#### Benchmark record template

| Field | Record |
| --- | --- |
| Workflow and target | The user-visible problem and agreed outcome. |
| Source/environment | Actual revision, configuration, hardware, runtime, and data shape. |
| Method | Workload, warm/cold state, repetitions, metric, and variation. |
| Baseline/result | Measured before/after values from comparable conditions. |
| Trade-offs | Correctness, error rate, resource cost, complexity, and limitations. |

Leave an unavailable value unknown. Do not fill a table with invented measurements or present a favorable single run as a general guarantee.

#### Example: a slow data view

Trace whether time is spent in repeated queries, oversized results, external calls, rendering, or contention. Fix the demonstrated cause. A relevant index or smaller projection may be sufficient; adding Redis is a separate design choice, not an automatic next step.

If caching is accepted, verify scope, freshness, invalidation, capacity, authorization, and fallback. Measure both hits and misses. If concurrency is increased, check resource limits and duplicate/partial external outcomes.

#### Verification gate

A faster isolated benchmark passes only its stated experiment. The changed workflow still needs relevant correctness and failure checks. If the target was achieved by dropping required work or weakening a control, the original acceptance criterion remains unmet.

### Acceptance checklist

- **Baseline:** The actual problem and representative baseline are recorded.
- **Cause:** The change targets an evidenced constraint.
- **Comparison:** Before/after results use comparable conditions and honest scope.
- **Quality:** Correctness, security, accessibility, reliability, and resource cost remain acceptable.
- **Outcome:** The agreed target is met or remaining work is clearly reported.
