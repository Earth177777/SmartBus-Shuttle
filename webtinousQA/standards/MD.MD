## 1. Purpose and writing quality

Documentation should let the intended reader understand the project, use it safely, change it correctly, and recover from relevant failures. Write clear, professional language with specific actions and observable outcomes. Explain business value when it helps the audience; retain the technical detail needed for engineering and operation.

Distinguish current behavior, accepted decisions, proposals, unknowns, and historical records. Do not invent functionality, deadlines, measurements, compliance, or verification results to complete a template. Update affected documentation with meaningful behavior or operational changes.

## 2. Proportional structure

Choose the smallest useful structure:

- Compact: a README and a few linked sections may cover a script, small tool, or experiment.
- Standard: a root README, documentation index, and focused topic pages suit a maintained application or library.
- Extended: larger, operationally critical, multi-component, or regulated projects may need separate owner, component, procedure, and evidence records.

Profiles are descriptive, not mandatory folder trees. Reuse existing locations and external systems of record. Do not create empty documents, duplicate trackers, or introduce infrastructure to satisfy a filename list.

Organize information logically around purpose, capabilities, implementation, development, operation, and history. These categories can be sections or directories. Every maintained page should be reachable from a suitable entry point.

## 3. Core information

Cover these topics to the depth needed by the project:

- Purpose, intended users, scope, constraints, status, and limitations.
- Supported first-use path: prerequisites, installation or setup, configuration names, actual execution/build/check commands, and expected results.
- Current components, important interfaces, data ownership, and relevant trust boundaries.
- Contribution and verification approach, known issues, and where to find current work.
- Accepted project decisions, major changes, release/support policy, and ownership.

A local script can describe several topics in one short document. Critical systems require enough detail for safe handover and recovery.

## 3.1 GitHub README standard — identity, function, and first use

**The repository README MUST function as the product's useful front door.** A visitor must quickly understand the program's name, purpose, core functions, intended users, current state, and how to achieve a first useful result. A polished design supports those tasks. A logo, banner, screenshot, badge collection, or internal documentation directory alone does not meet this requirement.

### Required visual opening

Start with the actual **program name**, its approved **logo or product banner when available**, and a concise plain-language statement of what it does and for whom. Always show the product name in text and its core functions near the top, even when an image already contains them. Use the real product name; naming a new product is a material product decision when not already established. An accepted wordmark/text treatment is a usable fallback while an approved logo is unavailable; never invent an official logo or silently rebrand an existing app.

Show roughly three to six principal capabilities, or the smaller real set, in a short list or readable Function / User outcome table immediately after the opening. Describe actual supported behavior in useful language. Mark planned, partial, experimental, or separately licensed capabilities accurately. Never make core functionality discoverable only inside an image, animation, release note, or distant specialist guide.

Use the required Webtinous · by Continous Group credit alongside accurate product/client identity under DESIGN.MD. Preserve other authorized ownership and license notices. Keep the program's identity and function prominent; company credit does not replace them.

### Consistent, polished Markdown design

Use a cohesive opening image/wordmark, clear heading hierarchy, a short navigation row for a long README, selective bold, short paragraphs, compact comparison tables, and well-labeled examples. Apply the project's approved visual identity and suitable Webtinous treatment. Keep a consistent section order across repositories while tailoring actual content to the product.

Use GitHub Flavored Markdown and repository-relative image/file links where appropriate. Keep README support assets under `webtinousQA/assets/` unless an existing canonical or tool-required location applies. Reference paths relative to the README's actual location. Provide meaningful alternative text, legible text sizes in screenshots, and images that remain readable in supported GitHub light/dark views and narrow layouts. Prefer a lightweight static image; motion must not be essential to understand or start using the product.

Use a real screenshot or short example of the primary workflow when it helps users understand a visual app. For a CLI, library, script, service, or hardware project, show a relevant invocation, input/output, consumer example, request/response, or supported device workflow instead of inventing a GUI. Caption demos with their actual version/state and sanitize data.

Retain the collection's Markdown-only presentation rule: **do not add raw HTML layout snippets, custom CSS, scripts, or an HTML reader**. A product logo/banner and selective imagery can make Markdown distinctive without hiding required instructions. Use badges only for genuine, current, checkable version/build/license facts with working destinations. Omit invented certification, test status, download counts, or unsupported marketing claims.

### README content and order

| Order | Section | What it must help the reader do |
| --- | --- | --- |
| 1 | Identity and purpose | Recognize the program by name and approved logo/wordmark, understand its purpose/audience, and see required attribution. |
| 2 | Core functions | Understand the principal supported capabilities and user outcomes; see a real example/demo where useful. |
| 3 | Quick start | Complete the shortest supported first-use path with prerequisites, relevant commands/actions, and an expected result. |
| 4 | Installation and configuration | Find supported platforms/versions, actual install/setup steps, necessary configuration names, and safe example values. |
| 5 | Usage | Perform representative tasks with inputs/outputs, important options, limitations, and links to deeper guides. |
| 6 | Documentation and development | Find relevant architecture/API/maps, developer setup, actual check/build commands, and the mandatory Webtinous starting SOP. |
| 7 | Versions and changes | Find the current supported release, compatibility/migration guidance, canonical CHANGELOG/UPDATELOG, and actual release links when they exist. |
| 8 | Help, contribution, and rights | Find support/issue reporting, contribution/security-reporting routes where established, actual license/rights, maintainer details when known, and accurate credits. |

Combine adjacent sections for a small product and omit irrelevant subsections with proportionate explanation; retain the essential identity, function, first-use, usage, help, and rights information. Public users should be able to get started before reading internal engineering process. Link the developer SOP without requiring ordinary users to study every QA module.

For quick start and installation, inspect and use the project's real supported workflow. State where a command runs, prerequisites, necessary configuration, and an expected successful result. Do not invent a package name, download URL, command, default credential, supported platform, license, or working hosted demo. Docker instructions apply when Docker is actually accepted for this project. If a crucial first-use step cannot be verified, state the concrete limit rather than presenting it as tested.

### Placement and ongoing maintenance

Use the existing canonical GitHub repository README, normally root `README.md`, preserving the project's filename convention. **The repository's public/developer README remains in its discoverable repository location; `webtinousQA/README.md` is the QA/documentation index and has a different job.** This explicit placement rule is compatible with keeping generated working records inside webtinousQA/. Link the two rather than replacing the repository README with an internal standards directory or maintaining competing copies.

Check which README GitHub will actually surface if `.github/`, root, or docs/ contain alternatives. Avoid an unintended stale file overriding the intended front page. Update affected descriptions, examples, screenshots, setup/usage, supported versions, release links, and limitations whenever behavior or delivery changes. Update corresponding changelog/update-log records under this standard.

### README acceptance check

- **Recognition:** Program name is readable in text; approved logo/banner or an accepted text fallback identifies it; Webtinous credit and third-party notices are accurate.
- **Function:** The purpose, intended audience, real core capabilities, and current limitations are clear near the beginning.
- **First use:** A reader can follow the supported setup and usage path to an expected result, with actual verification or a stated limitation.
- **Navigation:** Important documentation, developer SOP, versions/change records, help, and actual license/rights are findable with working links.
- **Rendering:** Markdown, code samples, tables, images/alt text, and relevant theme/narrow-view behavior were reviewed using available rendering; do not claim a GitHub render was checked if only a local preview was seen.
- **Freshness:** Product/version claims and examples match the actual source/release scope; placeholders, broken assets, sensitive data, and false badges are absent.

Reference: [GitHub repository README guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes).

## 4. Conditional topic register

Add or link deeper documentation only when the topic exists:

- API, library, message, file, or device contracts when consumed by others.
- Database/schema/migrations when structured persistent data exists.
- Storage, retention, deletion, backup, and restoration when durable data matters.
- Authentication, authorization, tenant boundaries, privacy, and security controls when relevant.
- UI, branding, responsive behavior, themes, and assistance when such interfaces are included.
- Packaging, containers, deployment, hosting, networking, workers, and scheduled jobs when used.
- Monitoring, incident response, on-call ownership, service levels, and recovery procedures when operational risk warrants them.
- Benchmarks, performance budgets, hardware interfaces, or media production records when part of scope.

Docker documentation is conditional on the project's accepted Docker use. Do not add Docker or another tool to make its document applicable. An accepted alternative can meet the same operational outcome.

## 5. Authority and decisions

**Keep one canonical source for each fact or topic; summaries link to it.** Identify whether a source owns policy, intended behavior, observed implementation, generated contracts, or historical facts. When sources conflict, record the discrepancy and resolve it with the appropriate owner. Do not silently treat intent as implementation or an accidental bug as approved policy.

Use the project decision record to preserve major technology and product choices. Record context, accepted option, scope, rationale, alternatives, consequences, status, and supersession. For new projects, resolve missing major decisions with the user; established decisions do not need renewed approval for routine work.

## 6. Authoring and maintenance

**Use descriptive titles, logical headings, stable links, consistent terms, and copyable examples appropriate to the actual stack.** State where commands run, prerequisites, expected effects, and important recovery limits. Clearly label examples and placeholders; unsupported example commands must not appear as verified setup steps.

Use unambiguous dates such as YYYY-MM-DD; include a timezone for event timestamps. Record owner, status, version scope, and review information when useful. Historical entries should remain truthful; use attributable corrections and supersession rather than erasing context.

Maintain diagram sources and explain complex visuals in text. Screenshots should supplement instructions and be sanitized. Generated documents must identify their source and update command; do not edit generated output as if it were canonical manual guidance.

## 7. Work, issue, and feature records

Record actionable defects with impact, reproduction, expected/actual behavior, affected scope, workaround, and resolution evidence where available. Track tasks with an outcome and acceptance criteria. Features should distinguish planned, partial, implemented, verified, deprecated, and removed states.

Use the existing tracker where it is canonical. Local documentation should explain ownership, access, and relevant views without duplicating every live ticket. Do not invent priority, dates, or owners. Distinguish a historical fix from the current status of an issue.

## 8. Agent instructions, secrets, and Git

**Follow the project's accepted policy for agent instruction files such as AGENTS.md and CLAUDE.md.** This standard does not universally require them to be committed or ignored. For a new project, ask before choosing a material sharing or retention policy. If local-only is required, exclude root and nested copies and avoid links that imply those private files are shared documentation.

Never put real secrets, tokens, private authentication state, customer records, or unnecessary personal information into documentation, examples, screenshots, or shareable archives. Commit sanitized templates where useful. Ignore generated caches, local outputs, and secrets according to the actual stack; do not ignore all Markdown, migrations, or source code through broad patterns.

## 9. Versioning, changelog, update log, and GitHub release documentation

**MD.MD owns the documentation policy for versioning, CHANGELOG, UPDATELOG, and GitHub release records. BUILD.MD executes the production release workflow under this policy.** The application's accepted authoritative version mechanism owns its actual version value; documentation must reflect that value rather than create a competing source. SOFTWARE.MD owns the shared engineering and decision rules. Resolve a material conflict before changing release identity.

### 9.1 Version identity and the user's decision

Record the current product/release-unit version, the last actual release, the proposed class and target, the accepted decision, and the source revision. Distinguish product version, documentation/standards version, package identity, platform build number, deployment identifier, and Git commit/tag. In a monorepo, identify independently versioned units explicitly.

For a requested app release, **ask whether the update is big/major, small/minor, or a fix/patch before changing release-version files**. Show the current version, your recommendation and reason, and proposed target. An explicit class or target already supplied for this release counts; do not ask twice. Base the recommendation on compatibility and actual scope, not line count. From 2.4.7, major becomes 3.0.0, minor 2.5.0, and patch 2.4.8. Reset lower components appropriately. Breaking public contracts generally require major treatment; compatible features fit minor; compatible fixes fit patch. Resolve ambiguous pre-1.0, prerelease, custom-version, and platform-code cases with the user.

Record the accepted target once and reuse it when resuming the same release. A failed build does not justify another increment. Preserve historical versions and released artifact contents. A documentation edit alone does not automatically authorize an app version bump, publication, deployment, or UI update prompt. Documentation-only version changes follow the actual project's accepted documentation/release policy.

### 9.2 Changelog: what changed in each release

**Maintain a truthful, release-focused CHANGELOG.** Use the existing canonical file when present. New generated project records default to `webtinousQA/documentation/CHANGELOG.md` and are indexed from `webtinousQA/README.md`. Keep a root or external canonical record when already established or tool-required; link it and avoid competing histories.

Maintain an **Unreleased** section for completed changes awaiting release, then entries for actual released versions with actual release dates. A candidate, planned date, draft GitHub release, or successful build must not be presented as a published release. Group meaningful changes as Added, Changed, Fixed, Deprecated, Removed, or Security where applicable; omit empty categories.

Explain user/developer impact, compatibility, migrations or required actions, relevant issue/PR references, and known limitations. Summarize actual work rather than copying every commit message. Separate verified shipped behavior from plans, incomplete features, and experiments. Route sensitive vulnerability details through the approved disclosure process rather than exposing them in a public changelog.

Before a release, reconcile the entry against actual changes since the correct previous release, including relevant unmerged/uncommitted candidate changes where appropriate. On an actual authorized publication, finalize its version/date and release links. Preserve older entries; make clear, attributable corrections instead of silently rewriting history or inventing earlier releases.

### 9.3 Update log: how the project and documentation progressed

**Maintain an UPDATELOG for meaningful work and documentation progress between releases.** New generated records default to `webtinousQA/documentation/UPDATELOG.md`; respect an existing canonical location/name. This log records work chronology and status, while the changelog explains released product changes. Small projects may use clearly separated, indexed sections in one canonical document if that avoids duplication while retaining both purposes.

For each meaningful entry, record the actual date and timezone where a time matters, task/outcome, affected areas or documents, current status, accepted decisions or linked decision records, checks and observed results, blockers/known limits, and the next useful action or handoff. Identify author/reviewer only when known. Link existing issues, PRs, notes, maps, and evidence rather than copying their full contents.

Use clear states such as Planned, In progress, Implemented, Verified, Blocked, and Released only when supported by evidence. Update the log at useful work boundaries, material decisions, verification, and handoff; do not create noise for each keystroke. A log entry is not approval or test evidence by itself. Do not expose secrets, private customer information, or unapproved internal discussion in shareable records.

### 9.4 GitHub versions, tags, and releases

**When the project uses GitHub, keep the confirmed app version, release tag, release title/notes, source revision, and attached package identities consistent.** Reuse its accepted tag convention, such as `v2.5.0` or a package-specific monorepo tag; do not impose a new scheme incidentally. A branch name or the word latest is not reliable proof of a production version.

GitHub Releases are based on Git tags. Verify that the intended tag resolves to the exact source revision containing the confirmed version, required documentation, and tested candidate. Build notes must identify the actual candidate when unrelated work remains. Do not move a published tag to disguise different contents, overwrite a released package under the same version, or claim a draft is published. Follow established tag protection and signing requirements using authorized tooling.

Prepare GitHub release notes from the reconciled changelog, including scope, compatibility/migration instructions, known issues, supported targets, installation/upgrade guidance, and actual artifact/checksum links. Review automatically generated notes for the correct previous tag, completeness, accuracy, and appropriate public content. GitHub's source-code archives are distinct from built installers or packages; do not present a source archive as a tested binary installer.

Choose draft, prerelease, stable/latest, and any channel according to the accepted release scope and actual readiness. Verify the repository, tag, target revision, previous release, asset versions/checksums, and links before an authorized final action. Record the actual release URL and publication time after publication is observed. If GitHub is not used, mark this section not applicable and apply equivalent traceability to the actual distribution channel without introducing GitHub.

MD.MD authorizes maintaining relevant documentation within the task's scope. It does not by itself authorize pushing commits, creating remote tags/releases, publishing packages, deploying, notifying others, or changing access. Reuse explicit existing authorization; ask only where required scope or a material decision is genuinely missing. Never claim those remote actions happened based on local files alone.

### 9.5 Documentation gate for a release

Before a candidate is called ready, verify that the accepted version agrees across relevant manifests, build/platform metadata, documentation, changelog, release notes, proposed/existing tag, and actual package. Update affected setup, contracts, maps, support/version records, migration/recovery instructions, and known issues. Check meaningful links and commands. A stale critical installation or upgrade instruction is a readiness defect.

Use BUILD.MD to execute production preflight, packaging, actual installation/upgrade checks, checksums, and handoff. Link the release report under `webtinousQA/reports/releases/<version>/README.md` to the canonical changelog, update log, relevant decisions, evidence, and actual publication state. Report failed, blocked, or unrun checks honestly; a completed template is not a passing release gate.

References: [Semantic Versioning](https://semver.org/spec/v2.0.0.html), [GitHub releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), and [GitHub automated release notes](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes).

## 10. Procedures and evidence

For risky operations, document trigger, owner, environment, access, preconditions, steps, expected results, verification, and rollback or forward recovery. Cover data separately from application code. A theoretical recovery plan is not evidence of a successful restore.

Record checks as Passed, Failed, Blocked, or Not run with scope and evidence. Distinguish source inspection, test execution, actual integrations, deployment, and physical validation. Do not claim readiness beyond the observed scope.

## 11. Review and completion

**Check affected links, anchors, examples, paths, actual commands, terminology, and implementation claims using proportionate means.** Run existing relevant documentation checks. Do not create a product test suite solely to verify prose.

The documentation is complete when readers can find the applicable information, current instructions agree with the supported implementation, proposals are labeled, major decisions and limitations are visible, and no sensitive content is exposed.

## Practical examples and reference

### A readable document pattern

1. **Purpose and scope:** identify the reader, outcome, and applicable system or version.
2. **Quick start:** provide a verified first useful action and its prerequisites.
3. **Decisions and constraints:** distinguish accepted choices, proposals, assumptions, and exclusions.
4. **Detailed guidance:** use heading levels, concise paragraphs, lists, tables, and labeled examples.
5. **Verification and recovery:** state expected results, actual checks, and what to do when an operation fails.
6. **References and history:** link the canonical sources, owner, related procedures, and material changes.

Keep navigation proportional. A small tool can combine these in a README; a larger project can use a linked portal. Avoid one giant unstructured page and avoid splitting every paragraph into a separate file.

### Readable Markdown

Use Markdown headings and selective bold as the common format. Use fenced code blocks for commands, valid tables for comparisons, descriptive links, and a short contents list. A simple banner image with meaningful alternative text can identify a GitHub repository. Keep essential setup and decision rules visible in the document.

Do not include credentials, internal-only links presented as public instructions, misleading badges, or unsupported “passing” status labels. A version badge can describe an actual version; a test badge must refer to real checks. Keep the reusable instructions in readable Markdown.

### Decision and verification notes

A decision record should state context, option, scope, basis, rationale, consequences, and status. A verification record should state the check, environment/source identity, observed result, date, evidence, and limitations. An authoring template is not proof that either activity occurred.

## Acceptance checklist

- **GitHub README:** Program identity/core functions, useful setup/usage, navigation/help, true version/rights, and readable visual design satisfy section 3.1.
- **Navigation:** Readers can find the applicable setup, decisions, procedures, and reference pages.
- **Accuracy:** Current behavior, planned behavior, and historical facts remain distinct.
- **Examples:** Copyable instructions match the supported tools and actual paths.
- **Presentation:** Headings, bold, tables, lists, and code blocks improve scanning without hiding essential content.
- **Version records:** Accepted version, changelog, update log, release notes, and applicable GitHub tag/release records agree with actual source and artifacts.
- **History:** Unreleased, candidate, draft, prerelease, and published states remain accurate; historical releases are preserved.
- **Evidence:** Links and important claims were checked; private content and misleading badges are absent.
