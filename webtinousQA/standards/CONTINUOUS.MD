## 1. Purpose and activation

Help users understand what is happening, what needs attention, and what they can do next using information the product can actually observe. This module applies only when contextual assistance or guided help is included in the project.

Continue the existing approved implementation. For a new integration, ask before choosing a substantial tour library, rules engine, model/provider, external service, learning capability, or privacy architecture. A local rule system, static help, native guidance, guided tour, or model-based assistant may be appropriate; none is required universally.

## 2. Existing Continous profile

**The earlier “Continous by Webtinous” experience is a named optional product profile.** Its reference design uses local rules and application state for explanations, with Driver.js for web guided tours. Preserve those established choices in a project that already adopts that profile; do not assume every project needs this assistant feature name, library, or the same capabilities. The Webtinous by Continous Group identity required by DESIGN.MD still applies.

Driver.js and other third-party components retain their own authorship and licensing. Product branding must not imply ownership of an external library. Adding this standard alone does not install or enable Continous.

## 3. Observable facts and status

**Define available topics, data sources, refresh behavior, timestamps, permissions, and evidence limits.** Explanations must distinguish observed facts, stale information, unavailable checks, documented intent, and uncertainty.

Use clear status semantics, such as Passed, Warning, Failed, Disabled, Checking, and Unknown, according to the implementation. A disabled check is not a passing check and should not inflate enabled-check success counts.

Explain exactly what a result establishes. Detecting a device is not a physical-operation test. Checking a destination is not proof a file was delivered. A pending task is different from completed work. Do not give confident answers where the application lacks evidence.

## 4. Questions, actions, and authority

**Separate answering a question from changing state.** Explain the current condition and useful next action. Recovery actions must follow the product's permission and confirmation model, report actual outcomes, and refresh relevant evidence.

Do not infer authorization from a question, a help article, or third-party content. Guidance must not bypass business approval, access control, payment decisions, physical safety procedures, or the user's control over consequential actions.

Supported language and conversation behavior must match the real implementation. A keyword/rule matcher should not be described as understanding arbitrary language, maintaining long conversational context, or learning from a question unless those capabilities actually exist.

## 5. Guided tours and accessibility

**Show relevant controls in their actual supported state.** Use stable targets, understandable steps, progress where helpful, and suitable next/back/close behavior. Handle missing targets, navigation, permission differences, loading, narrow screens, and relevant themes.

Keep tours dismissible or pausable where appropriate. Manage focus, keyboard access, assistive technology, reduced motion, and reading order. Do not obscure essential controls or reset user work. Provide suitable non-visual or non-tour help when needed.

## 6. Privacy, connectivity, and personalization

**Document whether questions and application state stay local or are sent to an external service.** A local explanation can still rely on a network check; state those boundaries separately. Limit transmitted and retained data to the accepted purpose and permissions.

Learning and personalization are optional capabilities requiring an accepted design. Define eligible inputs, retention, reset behavior, permissions, and impact on existing results. Asking a question must not be described as training a model unless it actually does so under the project's approved policy.

Do not silently add telemetry, remote AI calls, account synchronization, or persistent memory to a local assistance feature.

## 7. Verification and completion

Check supported topics, evidence freshness, unavailable/disabled states, permission boundaries, actual recovery results, tour targeting, accessibility, and relevant device/theme behavior. For model-based assistance, assess factual grounding and allowed tool behavior according to the accepted architecture.

Document available capabilities and limits in plain product language. A useful assistant gives users accurate context and control; it does not claim unobserved success or imply that its presence makes the host application ready for production.

## Practical examples and reference

### Explanation contract

| Field | What the assistance should convey |
| --- | --- |
| Observation | What the application can actually see and when it was checked. |
| Meaning | The practical implication, without overstating certainty. |
| Limitation | Missing, stale, disabled, or unverified information. |
| Next action | A supported step, its prerequisites, and any required user decision. |
| Result | The observed outcome after an action and refreshed checks. |

A diagnostic explanation should help users make a decision, not inflate confidence through a generic positive message.

### Example: connection readiness

“Device detected” can explain a successful discovery check. It should not imply that a camera captured a valid image, a printer produced output, or a sensor measurement is accurate. Offer the appropriate supported test and describe what that next test establishes.

A disabled check should be excluded from enabled-check success counts. An unavailable destination should remain Unknown or Failed according to the actual condition; do not convert absence of evidence into a pass.

### New integration gate

When the application already uses local rules and Driver.js, continue that established scope. A new project should decide whether it needs help at all, whether explanations stay local, and which substantial dependencies or providers it adopts. Do not silently add remote AI, learning, telemetry, or persistent memory.

## Acceptance checklist

- **Grounding:** Explanations reflect observable facts, freshness, and uncertainty.
- **Authority:** Questions, suggestions, and state-changing actions remain distinct.
- **Help:** Tours and shortcuts target real controls with accessible behavior.
- **Privacy:** Connectivity, transmission, retention, and learning behavior match the accepted design.
- **Evidence:** The actual supported topics and recovery results were verified within stated limits.
